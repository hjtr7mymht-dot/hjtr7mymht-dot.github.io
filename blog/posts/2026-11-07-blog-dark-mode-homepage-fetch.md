博客和主页是两套页面，如果主题状态各管各的，用户在主页切了暗色，点进 /blog/ 又是一片亮，这种割裂感我最不想看到。还有首页的文章卡片，如果每次发完文都得回去手动补，写博客的摩擦就上来了。这篇记录一下这两块是怎么落地的：暗色模式怎么跟主页联动，首页怎么不再手摆、改成自己拉数据。

## 暗色模式：别重造一套，复用就行

我最早冒出的念头是「给博客单独写一套深色配色」。但主页早就是暗色可用的了——它有一套完整的 CSS 变量，颜色、圆角、阴影都在里面。博客要是再自立一套，等于维护了第二份要跟主页同步的状态，纯纯的重复劳动。

所以做法很笨也很省事：博客直接吃主页那套 CSS 变量，配色、字体、圆角、阴影全用同一组。主题状态也共用 `localStorage` 的同一个 key——你在主页切成暗色，点进博客自动就是暗色，反过来也一样。用户根本感知不到这是两个站，只觉得「这站整体是暗的」。

这个思路的维护成本几乎为零。我主力机是隐星 P15（i7-12700H 配 RTX4060），但这类静态站不吃机器性能，重点不在算力，在于「别给自己留第二套要同步的东西」。

## 首页自动拉数据：用 fetch 替掉手抄

博客生成器是 `build.py`，纯 Python 标准库、零依赖，读 `blog/posts/*.md` 出文章页、首页和 RSS。首页那块我让它顺手把取数也接管了：用 `fetch` 直接读 `blog/feed.xml`，把最新几篇自动拉成卡片；GitHub 那边的 star 和 repo 数也改成走接口实时取，而不是我手抄一个写死的数字。

这么做之后，发文章的流程就收敛成一条线：新建一个 `YYYY-MM-DD-slug.md`，填六行 front-matter，跑一下 `python3 build.py`，提交，推送。首页卡片和 RSS 都是生成阶段顺带产出的，不用再回去手动补。当初把生成器设计成「丢一个 Markdown 就出网页」，正是为了让发布这件事足够轻——轻到几乎没有心理负担，才容易一直写下去。

## 一点体会

这两件事单独看都不难，难的是「在搭生成器时就替未来的自己省事」。复用现成的 CSS 变量、用 `fetch` 替掉手抄，都不是什么高深技巧，但每一处都让发布更轻一点。博客这东西，能一直写，比写得多重要得多。
