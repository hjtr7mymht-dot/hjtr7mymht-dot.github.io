2026 年 11 月 5 日 Python图像识别自动化

WOA_AutoBot 是怎么用图像识别替我打理机场的

从截图、识图到点下去，一条完整的自动化链路是怎么搭的——状态机、模板匹配、同帧批匹配，以及为什么要这么做。

WOA_AutoBot 是我目前最花心思的项目：一个给《World of Airports》用的自动化辅助工具，目标是把机场里那些重复的地勤、维修、起飞流程接过来，让人只在关键时刻做决策。目前 46 星，macOS 和 Windows 双平台都支持。

这篇不写使用教程，写实现思路——整条链路是怎么跑通的。

核心问题：游戏界面只有像素

自动化一个游戏，没有 API 可用，没有 DOM 可查，你唯一能拿到的东西就是屏幕截图。

所以整个工具的本质就是不断重复一个循环：

截图 → 判断现在在哪个界面 → 找到可点的按钮 → 点下去 → 验证有没有生效

难点全在"判断"和"找"这两步。

第一步：截图方案要能自愈

不同设备、不同系统，能用的截图手段完全不一样。我支持了四种：

  • ADB 截图 —— 兼容性最好，谁都能用
  • uiautomator2 截图 —— macOS 上性能更优的方案
  • nemu_ipc —— MuMu 模拟器专属的高速通道，仅 Windows
  • DroidCast_raw —— 备选方案

关键不在"支持了几个"，而在方案自检与自动回退：启动时挨个试，哪个可用就用哪个，跑着跑着失效了就自动换下一个。用户根本不需要理解这些名词，选不上就自己退回去了。

同样的思路也用在触控上——ADB 和 uiautomator2 两种触控方式可以互相兜底。

第二步：判断"我在哪"，靠状态机

早期版本是"看到什么图标就点什么"，结果弹窗一叠加就乱套。重构后改成五状态状态机：

  1. 主界面
  2. 任务详情
  3. 塔台菜单
  4. 弹窗
  5. 过渡动画中

每一帧先判定状态，再决定这个状态下哪些区域的匹配结果才算数。过渡态直接跳过，不误点。这一步做完，误操作率直接掉下去一个量级。

第三步：找按钮，模板匹配 + 颜色语义

按钮找位置用的是 OpenCV 模板匹配，但纯匹配不够稳——同一个按钮在亮色/暗色主题下长得不一样，游戏里还有"高亮可用"和"灰置不可用"两种状态。

所以加了亮/暗颜色语义自动矫正：先采样按钮周围区域的亮度，判断当前是亮主题还是暗主题，再决定匹配哪套模板、以及匹配到之后"这个按钮现在是可点的吗"。

筛选按钮还做了模板匹配 + 像素回退双重检测，一层失效还有另一层。

性能：一帧能干的事，绝不分开干

识图是 CPU 大户，优化围绕两件事展开。

同帧复用。 一帧截图拿到后缓存起来，这一帧内所有判断都复用它，而不是每个功能各自截一张。实测 3-5 倍加速。

同帧多图批匹配。 要找 7 种待处理图标？不是循环 7 次单图匹配，而是把 7 张模板拼成一张大图，一次搜索全部拿回。高频识别路径的 CPU 峰值明显降下来。

这两条加上之后，主循环的空闲间隔从 0.12s 压到 0.025s，有任务时从 0.02s 压到 0.005s——整体响应快了 4 倍以上，机器风扇倒是安静了。

坐标：设备物理坐标直连

不同分辨率的设备如果先归一化再换算，二次缩放的误差会累积，点着点着就偏了。

我的做法是物理坐标直连：模板匹配返回的是设备真实像素坐标，直接交给触控接口，中间不做任何换算。分辨率自适应只发生在"模板图是按某个基准分辨率截的"这一层，一次性算清。

兜底：工具必须比人更怕出事

自动化跑久了一定会遇到意料外的状态。三道保险：

  • 防卡死多次触发后自动停机 —— 不确定在干嘛的时候，停下来比乱点好
  • 暂停 / 继续 —— 人工介入后从当前状态恢复，不用从头开始
  • Web 控制面板 + 远程熔断 —— 浏览器里看多实例实时画面，出问题远程一键停

v1.5.1 之后还加了每日银币换金币这类定时任务，冷却时间写进配置，到点自动执行。

写在最后

这个项目对我最大的收获不是"做了个挂机工具"，而是把识图 → 决策 → 执行 → 验证这条链路完整跑通了一遍。它跟做物联网巡检、做数据采集本质上是同一件事：现实世界没有 API，你得自己从像素和字节里把状态读出来。
